# Experimental Windows crossfade input handle pinning

The test-only Windows `PinnedMedia::acquire` holds a set of read-only file handles opened with **`FILE_SHARE_READ` only**. As long as these handles remain alive, ordinary Windows opens requesting write access and delete/rename access should fail with a sharing violation. Files are SHA-256 verified **through the same retained handles** before the native render can consume their paths, rather than re-opening paths for the initial digest.

Safety checks: absolute paths, regular non-symlink file metadata, canonical duplicate rejection, exact saved byte lengths and SHA-256, bounded 64 KiB hashing, checked byte totals, and cooperative cancellation. On partial failure, owned handles are dropped automatically. Native Windows regressions test that writes and deletion are denied while the guard is held, that they succeed after release, and that changed content and duplicates are rejected.

**Important limitations:** The guard is not yet used by the renderer. Between validating a path and calling `open`, pathname replacement remains theoretically possible; verified handle identity is stronger than separate path reopens, but Windows reparse points, hard links, and the process that minted provenance need further scrutiny. `FILE_SHARE_READ` does not make existing or kernel-level writes impossible, and no guarantee is made for network shares or adversarial privileged processes. The eventual rendering integration must retain handles for every original and normalized part for the full encoder and publication lifetime, and validate installed-app behavior with FFmpeg. This is test-only code, no production export/UI changes.
